# Traefik NLB IP Target Migration — Test Summary

## Scope

- Date: `2026-07-27`
- Environment: `adev-use1-g2`
- AWS Region: `us-east-1`
- Migration target: `traefik-internal` Network Load Balancer
- Change: AWS NLB target type `instance` to `ip`

## Assessment

The migration appears successful based on the evidence collected so far. New
connections remained available, the pre-existing persistent connection
continued carrying traffic, all registered IP targets remained healthy, and no
load-balancer-generated resets or rejected flows were observed.

The CloudTrail timeline has been summarized below. The raw CloudTrail output
still needs to be attached as supporting evidence.

## Change sequence

### PR1 — target-type migration

Applied at `10:07:40 UTC`:

- changed `service.beta.kubernetes.io/aws-load-balancer-nlb-target-type` from
  `instance` to `ip`;
- enabled `preserve_client_ip.enabled=true`;
- retained the required target-group attributes.

This was the traffic-path change. AWS LBC was expected to create replacement IP
target groups, register Traefik Pod IPs, and repoint the existing listeners.

### PR2 — Kubernetes cleanup

Applied at approximately `10:44 UTC`:

- changed `externalTrafficPolicy` from `Local` to `Cluster`;
- set `allocateLoadBalancerNodePorts: false`;
- removed the instance-only
  `service.beta.kubernetes.io/aws-load-balancer-target-node-labels` annotation
  from the rendered Service.

PR2 was expected to leave the IP target groups and listener mappings unchanged.
This expectation will be checked against CloudTrail.

## Validation results

### Fresh TCP/TLS/HTTP connections

The continuous probe deliberately created a new TCP connection, performed a new
TLS handshake, and sent one HTTP request for every attempt.

Observed result:

- all recorded attempts returned `curl_rc=0`;
- all recorded attempts returned HTTP `200`;
- no client-visible failures or outage were recorded;
- the probe remained successful before, during, and after both changes.

### Persistent connection

The long-lived probe reused one TLS connection and continuously sent HTTP
requests over that connection.

Observed result:

- the connection continued carrying responses through PR1 and PR2;
- no unexpected migration-related closure was observed;
- the final `CLOSED` event was caused by the configured one-hour test duration,
  not by the migration.

### CloudWatch NLB metrics

Observed results:

- `TCP_ELB_Reset_Count`: `0`;
- `RejectedFlowCount`: `0`;
- `NewFlowCount_TCP` increased while the fresh-connection probe was running and
  returned to baseline when the probe stopped;
- `TCP_Target_Reset_Count` increased during the same interval as the intentional
  short-lived connection load and returned to baseline when that probe stopped;
- no client-visible failure correlated with the target-generated resets.

`TCP_Target_Reset_Count` counts TCP RST packets generated by targets and
forwarded by the NLB. It does not count failed HTTP requests or target restarts.
The metric cannot identify whether an individual reset happened before or after
a completed response. In this test, every measured request completed with
`curl_rc=0` and HTTP `200`, so the reset traffic did not represent an observed
request failure. Exact attribution of each RST packet would require packet-level
capture and is not required to determine the client-visible migration result.

### CloudTrail AWS timeline

The following command covered both PRs:

```bash
./cloudtrail-elbv2-events.sh us-east-1 2026-07-27T10:00:00Z 2026-07-27T11:00:00Z
```

CloudTrail recorded the following PR1 control-plane timeline. All times are UTC.

| Time | Observed ELBv2 operations |
|---|---|
| `10:07:41` | Replacement IP target groups were created and their attributes were applied (`CreateTargetGroup`, `ModifyTargetGroupAttributes`). |
| `10:07:42` | The existing listeners were updated to forward to the replacement target groups (`ModifyListener`). |
| `10:07:44` | Pod IP targets were registered in the replacement target groups and targets were deregistered from the old instance target groups (`RegisterTargets`, `DeregisterTargets`). |
| `10:07:47` | The old instance target groups were deleted (`DeleteTargetGroup`). |

The observed AWS reconciliation window lasted approximately six seconds, from
the first target-group operation at `10:07:41` through deletion of the old
target groups at `10:07:47`. This is a control-plane measurement, not an outage
duration.

CloudTrail recorded the listener updates before registration of the new Pod IP
targets. This demonstrates that the AWS LBC reconciliation was asynchronous and
that its high-level operations were not atomic. CloudTrail timestamps have
one-second resolution, so operations sharing the same timestamp cannot be
ordered more precisely.

No matching target-group or listener replacement operation was reported around
the PR2 cleanup time in the supplied findings.

## Conclusion

The available client-side, target-health, and CloudWatch evidence indicates a
successful migration from instance targets to IP targets without an observed
client-visible outage. The elevated target-reset count followed the synthetic
fresh-connection workload rather than the migration window and was not
accompanied by failed probe requests.

This test demonstrates the behavior of this development environment and traffic
pattern. It does not guarantee that every production long-lived connection will
survive a future migration; clients must still support reconnects.
